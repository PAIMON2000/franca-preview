# 013 运行时字形渲染层立项（thcrap 式系统字体渲染）

日期：2026-10-24。来源：用户确认东方静态路线卡字形后，认可"运行时注入 + 系统字体栅格化"方向，并指出该层对多类游戏有复用价值。

**状态更新（2026-10-24）：路线 A 已落地并通过真机验收。** Touhou 启用路径改走 thcrap 注入路线：`TouhouThcrapService` 生成 franca 补丁（jdiff 对话译文 + Noto Sans SC 字体 + base_tsa 依赖），存根 exe（`franca-thcrap-stub.exe`）交换游戏 `thNN.exe` 使 Steam 直接启动也走注入（fail-open 回落原版）；静态补丁态前置自动恢复原包。th11 真机局内对话简中渲染用户确认可用（验收记录 tests/2026-10-24-touhou-thcrap.md）；菜单/符卡名/结局/启动器对话框未翻译为已知边界。`--probe-touhou-thcrap` failures=0。

## 问题

东方 ZUN 引擎（th10/th11）以字形精灵图（text.anm）渲染文本，早期静态路线（静态适配器 v1）即使翻译正确也无法显示简体字；且 cp932 写回已在编码层损毁非 JIS 字符（2026-10-24 实机解包验证：简体译文大量变 `?`）。菜单文本硬编码于 exe、标题 logo 为图片，均不在静态文本路线内。**结论：ZUN 系可读中文的唯一现实路径是运行时渲染层。**

## 方案概述（参考 thcrap，未接入）

- 运行时注入游戏进程，钩住文本渲染调用；
- 拦截后按字符用系统字体（GDI/DirectWrite）现场栅格化为位图，缓存入纹理再交游戏绘制；
- 字符按需生成，任意文字（简中/韩文等）无需预制字形表；对话、菜单、结尾名单全界面生效。

## 范围与阶段

- **阶段 1（本立项目标）**：th10/th11 注入渲染层 + 简体字形显示，与静态 .msg 翻译管线组合验收；验收标准 = 真实游戏画面（对话与菜单可读简中），不接受解包/探针通过代替。菜单 exe 字符串与字形层配套后评估是否纳入；标题图为图片，翻译需重绘，不属本层。
- **阶段 2（复用，暂不承诺）**：渲染钩子按引擎各写各的，"多游戏复用"成立的只是系统字体栅格化与纹理缓存这一半，注入点与渲染管线适配仍是逐引擎工程。不在文档中写成通用能力。

## 许可证核实（2026-10-24）

thcrap 主体为 **The Unlicense**（公有领域奉献，见仓库 UNLICENSE.txt），可自由复制/修改/再分发/捆绑二进制，无 copyleft 义务。两条接入路线由此都可行：

- **路线 A（快）**：随附 thcrap 二进制，Franca 生成本地补丁（译文走 thcrap 补丁机制，字形由其运行时渲染层处理），经 thcrap_loader 启动游戏。前提是恢复原包（`.frorig`）、关闭其自更新；需学习其补丁 JSON 结构与本地补丁仓库托管方式。
- **路线 B（自持）**：移植其字形栅格化/渲染钩代码进自有注入层。工作量大，但代码可自由取用。

## 已知工作与风险

- 菜单等图片化文字（2026-10-24 取证：th11 title01.png 精灵图，exe/dat 无对应文本）：采用"ANM 精灵矩形精确切格 + 人工校译小词表 + 本地字体渲染回 PNG"的零模型方案（一次性生成静态补丁资源）。**不采用 OCR 路线**：菜单为哥特式装饰字体，OCR 误识率高；且内容已知、矩形已知，OCR 只增加不确定性。OCR 驱动仅在将来面对"未知游戏的未知文字图"时再评估（RapidOCR 系 CPU 可用，但美术字仍是短板）。
- 注入器本身（现有 src/Loader 实验或第三方注入手段评估）、th11 渲染调用点定位（thcrap 源码为现成参考，注意其许可证与声明，接入时核对 docs/THIRD-PARTY-NOTICES.md）；
- 字形缓存纹理管理、字号/换行边界对齐、与游戏原有排版冲突；
- 注入方式可能被杀软启发式误报；在线功能与反作弊场景需另行评估；
- 与现有 BepInEx/XUnity（Unity 路线）并行存在，架构边界需在动工前更新 architecture.json。
